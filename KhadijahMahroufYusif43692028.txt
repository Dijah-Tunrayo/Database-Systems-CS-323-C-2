THE VIEW STORES DISTINCT PART NUMBERS WITH ANY OF THEIR CONTACT COST BEING OVER 1000(POUNDS)
MAINTENANCE FOR SUCH A VIEW IS TRICKY MAINLY BECAUSE EVEN IF WE DELETE OR UPDATE AN EXPENSIVE ROW,
IT DOESNT MEAN THE PART IS AUTOMATICALLY REMOVED, THE OTHER CONTRACTS MIGHT STILL KEEP IT.

BASE TABLE ACCESS IS NOT NEEDED IN THESE INSTANCES
1. INSERTION OF AN EXPENSIVE ROW , YOU CAN JUST ADD PARTNO
2. UPDATING A CHEAP ROW TO AN EXPENSIVE ONE, YOU CAN ALSO JUST ADD PARTNO

THIS IS POSSIBLE BECAUSE THERES NO NEED FOR THE OPERATIONS TO CHECK IF OTHER ROWS EXIST

BASE TABLE ACCESS IS NEEDED IN THESE INSTANCES
1. THE DELETION OF AN EXPENSIVE ROW
2. UPDATING OF AN EXPENSIVE ROW TO A CHEAP ONE

THIS IS BECAUSE IT MUST CHECK IF ANY OTHER ROW FOR THAT PARTNO STILL HAS A COST OF OVER 1000(POUNDS), 
BASICALLY IT NEEDS TO QUERY THE BASE TABLE


WE CAN AVOID BASE TABLE ACCESS BY:
1. STORING AGGREGATE COUNTS IN THE VIEW INSTEAD OF JUST THE DISTINCT PART NUMBERS
2. AND THEN MAINTAIN THE VIEW BY INCREMENTING OR DECREMENTING COUNTS USING ONLY THE 
CHANGED ROW WHICH REQUIRES NO BASE TABLE READING

IN CONCLUSION
BASE TABLE IS AVOIDABLE FOR INSERTS AND COST INCRESEAS
BUT NOT FOR DELETES OR COST DECREASES, UNLESS THERE ARE ADDITIONAL METADAT STORED IN THE MATERIALISED 
VIEW ITSELF.
